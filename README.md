# CFMR Overview

CFMR is a 90-problem CUTEst test set for benchmarking derivative-free optimization
algorithms. It takes the 60 nonlinear least-squares problems of the CR set as its
core and adds EXT, an extension set of 30 general-objective problems that widens the
benchmark beyond least-squares structure. Both parts are transcribed from problem
tables of two papers by Cartis et al.; the CR+EXT pairing is specific to CFMR and is
not proposed by either paper. This repository provides the problem selection, SIF
parameters and published reference values in machine-readable form; it is an
independent third-party packaging, not released by the authors of those papers, and
adds no new problems or results.

## Problem Set Description

| Part | Role | Problems | Objective | Problems taken from |
|---|---|---|---|---|
| `CR` | core | 60 | nonlinear least-squares, residual vector `r(x)` available | Cartis & Roberts (2019), Table 3 |
| `EXT` | CFMR extension | 30 | general objective `f(x)`, no residual decomposition | Cartis, Fiala, Marteau & Roberts (2019) |

`CR` alone rewards solvers that exploit residual structure. `EXT` exists so that the
same run also covers problems where no such structure is available, which is what
makes CFMR a single 90-problem set rather than two separate benchmarks.

**Objective convention.** For `CR` problems, `f_x0_expected` and `f_star_expected`
are `||r(x)||² = Σ rᵢ(x)²`, taken from the `2f(x₀)` and `2f*` columns of Table 3 of
Cartis & Roberts (2019) — that paper writes the objective as `f = ½||r||²`, so its
tabulated `2f` is the sum of squares. `EXT` values are the objective as published,
with no factor. Values are stored exactly as the papers print them, so any row can be
checked against the source by eye. Each entry states its own units in
`objective_convention`; a solver interface that minimises `½||r(x)||²` reports half of
the `CR` values, so scale with `cfmr.rescale` before comparing. `cfmr.py` computes
`f(x0)` as `p.cons(x0)ᵀp.cons(x0)`, matching the stored convention.

The More–Wild convergence test is invariant to a positive rescaling of `f`, so entries
may differ in convention — but `f(x0)`, `f(x_k)` and `f_L` must share one convention
*within* an entry. Mixing them is the one way to get a wrong data profile with nothing
raising an error.

All problems have `25 ≤ n ≤ 120`. Each entry records the SIF parameters that
reproduce the paper's dimensions, the published `f(x0)` and `f*`, whether the problem
is bound-constrained, and an evaluation budget.

**Free variables.** `n` counts free variables, as the papers do. Several problems are
PDE discretisations whose boundary grid points are variables fixed by `bl == bu`;
CUTEst reports them in `n` unless they are dropped (BRATU3D: 27 free, 125 total). The
harness imports with `drop_fixed_variables=True` so that `n` matches the paper and no
solver can move a variable the problem holds constant.

**Budget.** `budget = budget_scale * (n + 1)` with `budget_scale = 50`, i.e.
50 simplex gradients per problem. The source papers do not use one budget throughout:
Cartis & Roberts (2019) report `200(n+1)` for their medium-scale runs and `50(n+1)`
for the large-scale ones, "commensurate with the greater cost of objective
evaluation". `budget_scale` is stored per problem so a harness can read the multiplier
rather than assume one; change it if your experiment needs a different figure, and
state which you used when reporting results.

Nine problems are bound-constrained: CHANDHEQ, CHEMRCTA, CHEMRCTB, EIGENA, QR3D,
QR3DBD and SEMICON2 in `CR`, BDEXP and SINEALI in `EXT`.

## Contents

| File | Description |
|---|---|
| `data/cfmr_problems.json` | The dataset: schema v2, `meta` + 90 `problems`, plain JSON, no dependencies |
| `data/cfmr_observed.json` | Measured companion: `f(x0)` and the best value reached from `x0` on one installation, with the toolchain that produced it |
| `cfmr.py` | Loader, problem resolution, CUTEst verification, registry and CSV export |
| `cfmr_profile.py` | Runs Py-BOBYQA over the set and draws its data profile |
| `f_star_audit.py` | Regenerates `data/cfmr_observed.json`; reports which tabulated `f*` a solver can go below |
| `test_cfmr.py` | Offline consistency checks; runs without CUTEst |
| `validate_pybobyqa.py` | Optional cross-check of the reference values with Py-BOBYQA |
| `cfmr_registry.json` | Generated by `cfmr.py build`: the dataset with `n`, `m` and `f(x0)` as measured on your CUTEst installation |
| `cfmr_problems.csv` | Generated: flat table for feeding a benchmark harness (`suite` column is `cfmr_cr` or `cfmr_ext`) |
| `validate_pybobyqa.csv` | Generated by `validate_pybobyqa.py`: per-problem solver outcome against `f*` |

The problems themselves are CUTEst/SIF files and are not redistributed here.

## Using the Repository

Reading the dataset requires only a JSON parser. The file has two top-level keys,
`meta` (schema version, convention definitions, citations) and `problems`:

```python
import json
d = json.load(open("data/cfmr_problems.json"))
assert d["meta"]["schema_version"] == 2
problems = d["problems"]
nls = {k: v for k, v in problems.items() if v["is_nls"]}   # the 60 CR problems
```

Or via the loader, which checks the schema version for you:

```python
import cfmr
problems, meta = cfmr.load(), cfmr.load_meta()
```

Each entry:

```json
{
  "suite": "CR", "name": "ARGLALE", "name_alt": [],
  "sif_params": {"N": 100},
  "sif_params_alt": [{"N": 100}],
  "n": 100, "m": 400,
  "objective_convention": "sum_of_squares",
  "f_x0_expected": 700, "f_star_expected": 300,
  "is_nls": true, "is_bound_constrained": false,
  "budget_scale": 50, "budget": 5050
}
```

`objective_convention` names the units of `f_x0_expected` and `f_star_expected`:
`sum_of_squares` (`||r||^2`, the CR entries) or `as_published` (the EXT entries). It is
redundant with `is_nls` by construction, and stated anyway — `is_nls` describes the
problem, `objective_convention` describes these two numbers, and reading the second off
the first is the assumption that silently produces a wrong data profile. `cfmr.rescale`
converts:

```python
f_star = m["f_star_expected"] * cfmr.rescale(m, "half_sum_squares")  # DFO-LS, DFBGN
```

`name_alt` lists names the same problem carries in other MASTSIF versions; the resolver
tries them in order when `name` does not import, and accepts one only if `n`, `m` and
`f(x0)` still match the paper.

`m` is the residual length (`pycutest.Problem.m`) for `CR` problems and `null` for
`EXT` problems. `sif_params_alt` lists candidate parameter dictionaries to try
in order: the papers write dimensions such as `N/2 = 50`, which state a dimension
rather than name a SIF key.

## Requirements

Verification requires [PyCUTEst](https://jfowkes.github.io/pycutest/) with CUTEst and
SIFDecode installed. PyCUTEst supports Mac and Linux only; on Windows it can be used
through the Windows Subsystem for Linux. Reading the dataset and running
`test_cfmr.py` require neither.

```bash
pip install pycutest numpy
export CUTEST=... SIFDECODE=... ARCHDEFS=... MYARCH=...
```

## Verification

```bash
python cfmr.py list      # print the set (no CUTEst needed)
python cfmr.py verify    # import all 90 problems, compare n, m and f(x0)
python cfmr.py build     # verify, then write cfmr_registry.json and cfmr_problems.csv
```

`verify` accepts a relative error of `1e-3` on `f(x0)`, which absorbs the drift
between CUTEst and SIFDecode versions.

`n`, `m` and `f(x0)` together fingerprint a CUTEst problem: a rename, a wrong parameter
set or a different fixed-variable convention moves at least one of them. `cfmr.py`
therefore refuses to hand back a problem whose fingerprint disagrees with the paper,
and `cfmr_profile.py` checks it *before* spending a budget — a mis-resolved problem
otherwise becomes a plausible-looking wrong point on a plot with nothing raising an
error. When `name` does not resolve, `name_alt` is tried; when the SIF decoder rejects
`sifParams` (`sifdecoder -param` drops the definition of the parameter it is overriding
for some files, e.g. SEMICON2, SEMICN2U and ODC in CUTEst as of 2026), the values are
baked into a private copy of the SIF under `mastsif_cfmr/` and the decoder is bypassed.
Either fallback is recorded in the registry's `param_note`; neither is accepted unless
the fingerprint still matches.

Problems are imported with `drop_fixed_variables=True` so `n` matches the papers; the
bounds of the surviving variables remain visible in `p.bl` and `p.bu`.

A problem that cannot be resolved is **never dropped from a data profile's
denominator**. It stays in the set, counts as never solved, and is named on the figure
and in the run's warning output — a benchmark that silently shrinks its denominator
reports a different number under the same axis label.

All 90 problems resolve and match on a live CUTEst installation: `n`, `m` and `f(x0)`
agree with the papers for 90/90, with no problem needing `name_alt` and three
(`SEMICON2`, `SEMICN2U`, `ODC`) needing the baked-SIF fallback. `f_star_audit.py`
re-measures `f(x0)` through an unrelated code path and also finds 90/90 agreement.
That was on:

| | |
|---|---|
| CUTEst | 2.7.1 (4 June 2026) |
| SIFDecode | 3.1.1 (15 May 2026) |
| MASTSIF | commit `29adac9f` (1 June 2026) |
| PyCUTEst | 1.8.2 |
| Python / NumPy / SciPy | 3.11.16 / 2.4.6 / 1.17.1 |

Those versions are recorded in `data/cfmr_observed.json` too. A different CUTEst or
MASTSIF can move a starting point, so run `python cfmr.py build` once on your own
installation and keep the resulting `cfmr_registry.json` with your results: it pins
the SIF parameters and starting values your runs actually used.

### Cross-checking with Py-BOBYQA

`cfmr.py verify` checks the starting values; `validate_pybobyqa.py` additionally
checks the reported minima by solving each problem with
[Py-BOBYQA](https://github.com/numericalalgorithmsgroup/pybobyqa), a general-objective
model-based DFO solver that applies to all 90 problems and needs no residual
structure.

```bash
pip install Py-BOBYQA
python validate_pybobyqa.py            # all 90 problems (slow: hours)
python validate_pybobyqa.py LUKSAN     # only problems whose key matches
```

Each problem is solved from `x0` within each problem's `budget`, respecting bounds
where present, and the final value is compared with `f_star_expected`; results are
written to `validate_pybobyqa.csv`. Reaching `f*` corroborates that the reference
value and the SIF parameters describe the same problem. **Not** reaching it proves
nothing about the dataset: many of these problems are not solvable to optimality by
any one solver within this budget, which is what makes them a benchmark.
Treat this script as a smoke test on the reference values, not as a benchmark run.

### Reference values are not certified minima

`f_star_expected` is what the source paper printed. A paper reports the minimum its
own solvers found, so on a multimodal problem a better solver can go below it — and
when it does, the More–Wild test

    f(x0) - f(x_k) >= (1 - tau) * (f(x0) - f_L)

is satisfied at every `tau` at once. The problem is then marked solved at every
accuracy level, silently, with nothing raising an error. `f_star_audit.py` measures
how far this reaches: it runs L-BFGS-B with CUTEst's exact gradients from each
problem's own `x0` and compares where it lands with the tabulated value.

On the installation above, **16 of 90 problems reach below their tabulated `f*`**, but
14 of those undershoot by a relative `2e-7` or less — that is the papers' printed
precision, not a lower minimum. Two are real:

| problem | f(x0) | f\*_table | best reached | relative |
|---|---|---|---|---|
| `EXT::BROYDN7D` | 350.984 | 40.12284 | 35.28061 | 1.2e-01 |
| `CR::LUKSAN22` | 24876.9 | 872.923 | 868.9146 | 4.6e-03 |

Both are stationary to `‖g‖∞ < 1e-6`. `BROYDN7D` at `n = 100` is strongly multimodal:
plain L-BFGS-B from the paper's `x0` already lands at 39.678, and perturbed starts
reach below 28. `LUKSAN22` is a `CR` problem, so this is not an artefact of the `EXT`
half.

What it costs, by accuracy level (denominator 90):

| tau | problems marked solved at every budget by a too-high `f*` |
|---|---|
| 1e-1 | 0 |
| 1e-3 | 1 |
| 1e-5 | 2 |
| 1e-7 | 4 |

τ=1e-1 and τ=1e-3 are essentially unaffected, which is where most published DFO
profiles sit. **τ=1e-7 is not reliable from tabulated values on this set**: 4 of 90 is
a large share of a curve that only reaches 15–20%, and two of those four
(`EXT::BOX`, `EXT::RAYBENDL`) are tripped by the table's *printed precision* alone —
at that `tau` the threshold width `tau * (f(x0) - f*)` is narrower than the rounding
in the published number. No transcription can fix that.

The remedy is to lower the floor rather than to edit the transcription:

```python
observed = cfmr.load_observed()
fL = cfmr.f_L(key, meta, observed, extra=[my_solver_best])
```

`cfmr.f_L` returns the smallest of the tabulated value, the measured value in
`data/cfmr_observed.json`, and anything you pass in `extra`. Every candidate must
come from a run started at the problem's `x0`. A value from global search would
tighten the target past what any solver starting there can reach and can leave a
problem unsolvable for all of them — which is why Moré & Wild define `f_L` as the
best value the compared solvers attain, not the global minimum.

`data/cfmr_observed.json` is a separate file on purpose. `cfmr_problems.json` holds
only what the papers print, so every row in it stays checkable against the source by
eye; measured numbers, which depend on a machine and a toolchain, belong beside the
machine and toolchain that produced them. Regenerate it with:

```bash
python f_star_audit.py                          # L-BFGS-B from x0, all 90
python f_star_audit.py --history run.json       # also fold in a solver run's f_final
python f_star_audit.py --report                 # print the table above
```

If your own run goes below the floor it was scored against, `cfmr_profile.py` says so
and names the problems: refresh the file with `--history` rather than publishing a
profile with a free point in it.


## Benchmarking Notes

- The 60 `is_nls` problems expose `r(x)` through `p.cons(x)`, with `f(x) = ||r(x)||²`,
  so residual-based solvers such as DFBGN and DFO-LS apply to them.
- The 30 `EXT` problems expose only the scalar `f(x)` through `p.obj(x)` and
  have no residual decomposition; residual-based solvers do not apply.
- The budget is `budget_scale * (n+1)` evaluations, `budget_scale = 50` in the data;
  read it from the data rather than hard-coding a multiplier. `cfmr_profile.py` sets
  its own `BUDGET_SCALE = 100` and says why in its config block — at 50 the τ=1e-5 and
  τ=1e-7 curves are still climbing when the budget ends, so the figure reports where
  the budget stopped rather than where the solver did. A profile must state which
  multiplier produced it; the two numbers are not interchangeable.
- Take `f_L` from `cfmr.f_L(key, meta, cfmr.load_observed())`, not from
  `f_star_expected` directly. See *Reference values are not certified minima* below.
- If a wall-clock limit is also needed, record timeouts as `∞` rather than as the last
  observed value, and report how many occurred.
- Set `OMP_NUM_THREADS=1` to stop BLAS from oversubscribing a process pool.
